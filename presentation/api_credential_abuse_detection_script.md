# API/Credential 악용 탐지 발표 대본

## 1. 표지 — API / Credential Abuse Detection

먼저 표지에 나온 주제부터 간단히 말씀드리겠습니다. 이번 프로젝트에서는 Kubernetes Audit Log를 이용해 정상적인 API 사용과 공격 의심 행위를 구분했습니다. 규칙으로 위험도를 계산하고, LLM은 그 결과를 사람이 이해하기 쉽게 설명하도록 연결했습니다. 지금부터 왜 이런 탐지가 필요한지, 실제로 어떤 기준을 사용했는지, 그리고 결과가 어땠는지 순서대로 말씀드리겠습니다.

## 2. 목차 — Contents

두 번째 슬라이드는 전체 발표 순서입니다. 먼저 문제와 실습 환경, 그리고 입력으로 사용한 로그를 설명하겠습니다. 다음으로 정상 요청과 공격 의심 요청을 구분하는 규칙을 살펴보겠습니다. 그 뒤 규칙 결과를 LLM이 어떻게 설명하는지 보여드리고, 마지막에는 실제 탐지 결과와 오탐·미탐, 한계를 정리하겠습니다.

## 3. 문제 정의 및 프로젝트 목표

세 번째 슬라이드에서는 왜 API와 Credential 악용을 따로 탐지해야 하는지 설명하겠습니다. Kubernetes API를 이용하면 Secret을 조회하거나 Pod 안에서 명령을 실행할 수 있습니다. Credential이 탈취되면 공격자도 정상 사용자와 똑같은 API를 호출할 수 있기 때문에, 로그인에 성공했는지만 봐서는 구분이 어렵습니다. 그래서 이 프로젝트에서는 호출한 주체, 요청한 리소스와 동작, 응답 코드, 호출 빈도를 Audit Log에서 함께 분석하는 것을 목표로 삼았습니다. 다음 슬라이드에서 이 목표를 시험한 환경을 보겠습니다.

## 4. 실습 환경 및 시나리오 개요

네 번째 슬라이드에서는 실습 환경과 입력 데이터를 설명합니다. 테스트 클러스터의 `pbl-security` Namespace와 `pbl-crypto-platform-app` ServiceAccount를 기준으로 했습니다. 기본 평가에는 저장소에 제공된 `normal.log`와 세 개의 `abnormal` 로그를 그대로 입력했습니다. 정상 로그에는 Pod·Service·ConfigMap 조회가 있고, 공격 로그에는 Secret 조회, Pod Exec, 짧은 시간의 반복 조회가 있습니다. 실제 Credential을 훔친 실습은 아니며, 필요하면 저장소의 스크립트로 같은 요청 패턴을 클러스터에서 재현할 수 있습니다. 이제 이 로그에서 정상과 의심 행위를 어떤 관찰점으로 나눴는지 보겠습니다.

## 5. 정상 행위와 공격 행위의 흐름 비교

다섯 번째 슬라이드에서는 정상 요청과 의심 요청을 비교합니다. 정상적인 사용자는 허용된 `pods`, `services`, `configmaps`를 조회하고 HTTP 200 응답을 받습니다. 반면 Secret 조회나 `pods/exec` 요청은 민감한 작업이므로 별도로 확인합니다. 이 요청이 HTTP 403으로 거부되면 실제 접근에는 실패한 것입니다. 하지만 누군가 민감한 API를 호출하려 했다는 기록은 남기 때문에, 차단된 요청도 탐지 신호로 포함했습니다. 다만 403 하나만으로 공격이라고 단정하지 않고 다른 징후와 함께 판단합니다. 다음은 이 판단을 처리하는 시스템 구성입니다.

## 6. 탐지 아키텍처

여섯 번째 슬라이드에서는 시스템을 구성하는 요소와 각 역할을 보여줍니다. 먼저 제공된 Audit Log를 읽고, 시간·사용자·리소스·동작·응답 코드·IP·User-Agent를 정리합니다. Rule Engine은 이 정보를 이용해 시간창별 위험 점수와 탐지 근거를 만듭니다. LLM에 전달할 때는 Finding에서 Token, Password, 요청 Body를 제거하고 필요한 정보만 구조화합니다. 마지막으로 `findings.jsonl`, `metrics.json`, `report.md`에 판정과 평가 결과를 남깁니다. 여기서 중요한 점은 Rule Engine이 라벨을 만들고 LLM은 그 라벨을 설명한다는 것입니다. 다음 슬라이드에서는 이 구성요소가 실제로 어떤 순서로 동작하는지 보겠습니다.

## 7. 방법론 도식 — Evidence to Decision

일곱 번째 슬라이드에서는 실제 판정 순서를 보여줍니다. 먼저 JSONL의 각 줄을 Audit Event로 바꾸고, 같은 ServiceAccount와 source IP의 이벤트를 시간순으로 정렬합니다. 첫 이벤트부터 300초 안에 들어온 요청을 하나의 Window로 묶고, 이 Window를 판정 단위로 사용합니다. 그 안에서 Secret 접근, `pods/exec`, 민감 요청의 403, 반복 열거, 기준 밖 IP·User-Agent 규칙을 검사합니다. 위험 점수와 rule id, 원본 line number를 저장한 뒤, 공격 또는 의심으로 분류된 Window만 민감정보를 제거해 LLM에 전달합니다. 따라서 이 단계에서 실제 라벨을 정하는 것은 규칙이며, LLM은 이후 설명만 담당합니다. 다음 슬라이드에서 점수가 어떻게 계산되는지 구체적으로 보겠습니다.

## 8. 탐지 규칙과 위험 점수

여덟 번째 슬라이드는 규칙 기반 방법론의 핵심인 점수표입니다. 허용된 `pods`, `services`, `configmaps`의 `get/list`와 HTTP 200은 정상 근거로만 기록하고 점수는 주지 않습니다. Secret의 `get/list`와 `pods/exec create`는 각각 60점, 민감 요청의 HTTP 403은 25점입니다. 300초 안에 8개 이상의 요청과 3종 이상의 리소스가 함께 나타나면 30점, 기준 밖 IP나 User-Agent가 나타나면 25점을 더합니다. 같은 규칙이 여러 번 발생해도 한 Window에서는 한 번만 점수에 반영합니다. 30점 미만은 normal, 30~59점은 suspicious, 60점 이상은 attack 라벨입니다. 예를 들어 Secret 조회와 403이 함께 있으면 60+25로 85점이 됩니다. 이제 이 규칙이 정상 로그에 적용되는 모습을 보겠습니다.

## 9. 정상 행위 예시

아홉 번째 슬라이드는 제공된 `normal.log`에 규칙을 적용한 결과입니다. 허용된 `pods`, `services`, `configmaps`만 읽고 동작도 `get`이나 `list`로 제한되어 있습니다. 응답은 모두 HTTP 200이고 User-Agent와 IP도 기준선과 같습니다. Secret, Pod Exec, 반복 열거가 없으므로 가중치가 붙는 규칙이 없고, 점수는 0점입니다. 따라서 이 Window는 normal 라벨이 됩니다. 다음으로 같은 규칙을 공격 패턴 로그에 적용해 보겠습니다.

## 10. 공격 행위 예시

열 번째 슬라이드는 제공된 세 개의 abnormal 로그에 같은 규칙을 적용한 결과입니다. `abnormal_1`은 Secret 조회 60점과 403 25점으로 85점입니다. `abnormal_2`는 `pods/exec create` 60점, 403 25점, 기준 밖 User-Agent 25점으로 110점입니다. `abnormal_3`은 Secret 접근 60점, 403 25점, 18개 요청과 3종 리소스의 burst 30점으로 115점입니다. 여기서 403은 공격 성공이 아니라 민감한 요청이 발생했다는 증거입니다. 이처럼 규칙이 먼저 근거와 점수를 만들고, 다음 단계에서 LLM을 연결합니다.

## 11. LLM 적용

열한 번째 슬라이드에서는 규칙 결과를 LLM으로 설명하는 과정을 보여줍니다. LLM은 최종 판정자가 아니며, 규칙이 만든 Finding에서 Token, Password, 요청 Body를 먼저 제거합니다. 이후 사용자, 리소스, 응답 코드, 점수, rule id처럼 필요한 정보만 JSON Schema 형태로 전달합니다. 예를 들어 Pod Exec이라면 “컨테이너 내부 명령 실행 요청이므로 계정 오용 가능성을 확인할 필요가 있다”고 설명할 수 있습니다. 동시에 승인된 장애 대응일 수도 있으므로 사용자, RBAC 권한, 승인 기록과 source IP를 확인하라고 안내합니다. 즉 LLM은 공격 사실을 증명하는 것이 아니라, 규칙이 남긴 근거와 조사 방향을 정리합니다. 다음은 기본 로그 네 개를 실제로 실행한 결과입니다.

## 12. 실제 탐지 결과

열두 번째 슬라이드는 기본 로그 네 개의 실제 탐지 결과입니다. 정상 Window는 규칙에서 바로 normal로 판단해 LLM을 건너뛰었고, 세 개의 공격 Window만 LLM에 전달했습니다. 세 사례 모두 LLM의 설명 라벨이 규칙 결과와 일치했습니다. 다만 confidence 0.95는 모델이 출력한 참고값일 뿐, 실제 공격 확률로 보정된 통계값은 아닙니다. 기본 사례에서는 정상과 공격이 뚜렷했기 때문에 모든 사례가 맞았고, 다음 슬라이드에서는 더 현실적인 오탐·미탐 조건을 추가해 평가했습니다.

## 13. 오탐·미탐 확장 평가

열세 번째 슬라이드는 기본 사례만으로는 보이지 않는 오탐과 미탐을 확인한 결과입니다. 확장 평가용 로그에는 승인된 운영자의 Secret 조회와 Pod Exec, 그리고 천천히 API를 조회하는 저속 정찰을 포함했습니다. 정상 작업 두 건은 민감 API라는 이유로 공격으로 잘못 판단했고, 저속 정찰 한 건은 반복 기준을 넘지 않아 놓쳤습니다. 그래서 Precision은 0.600, Recall은 0.750, F1은 0.667이었습니다. 이 결과는 명확한 공격은 잘 잡지만 승인 작업과 느린 공격을 구분하는 데 한계가 있음을 보여줍니다. 마지막으로 이 결과를 운영 환경에 적용할 때의 한계를 정리하겠습니다.

## 14. 한계와 개선 방향

열네 번째 슬라이드는 탐지기의 한계와 개선 방향입니다. 이번 평가는 하나의 Namespace와 ServiceAccount, 고정된 300초 Window와 점수를 사용한 작은 테스트입니다. Audit Log만으로는 장애 대응과 공격을 완전히 구분하기 어렵고, NAT나 프록시 때문에 정상 사용자의 IP가 다르게 보일 수도 있습니다. 반대로 공격자가 정상 속도로 천천히 움직이면 놓칠 수 있습니다. 운영 환경에서는 승인 티켓과 계정별 기준선을 연결하고, 네트워크와 런타임 로그도 함께 분석해야 합니다.

## 15. 결론 및 다음 단계

열다섯 번째 슬라이드에서는 전체 결론을 정리합니다. Secret 접근, Pod Exec, 403, 반복 호출을 함께 보면 API와 Credential 악용 가능성을 탐지할 수 있었습니다. 하지만 정상적인 관리자 작업은 오탐될 수 있고, 천천히 진행되는 공격은 놓칠 수 있습니다. 따라서 결과는 공격 확정이 아니라 추가 조사가 필요한 위험 경보로 사용해야 합니다. 규칙은 재현 가능한 분류를 만들고, LLM은 어떤 근거로 경보가 발생했는지와 정상 작업일 가능성을 설명합니다. 최종 판단은 분석가가 원본 로그와 승인 기록을 확인한 뒤 내립니다.

마지막 슬라이드는 발표 내용을 한 문장으로 정리하는 부분입니다. 제공된 Audit Log에서 규칙으로 위험 신호를 찾고, LLM으로 그 이유를 설명하며, 최종 판단은 분석가가 내리는 구조입니다. 이상으로 발표를 마치겠습니다. 경청해주셔서 감사합니다.
